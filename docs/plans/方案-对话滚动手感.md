## 一、P0：跟随判定的滞回与方向

### 现状（问题）

跟随只有一个开关，且两个方向的判定窗口都极窄：

```
list.rs:560   scroll_by(distance < 0)        → stop_following()   // 任何 1px 上滚都脱离
list.rs:949   scroll() 里 delta.y > 0        → stop_following()
list.rs:1222  layout 后重新吸附：scroll_offset + available_height >= total - px(1.0)
```

因为 `content.rs:340` 在 capture 阶段就 `stop_propagation`，list 自己的 bubble handler 不会跑，
实际脱离只由 `chat.rs:2007` 决定：

```rust
// chat.rs:2007
if delta < px(0.) { s.list.pause_following_tail(); }
```

于是有两个手感问题：

1. **任何一格上滚都立刻脱离**。往上看 5px 就丢跟随，再往下滚想恢复，得**精确滚到距底 1px 内**。
   `chat.rs:2037` 那段注释已经在对抗这一点：
   > 列表在「离底不到 1px」时会自动重新跟随，若紧邻重绘或小步长导致首帧位移不到 1px，
   > 流式追加会把视口拽回底部 —— 所以每帧再压一次 `pause_following_tail`

   用"每帧再压一次"来对抗 1px 窗口，说明阈值本身就不对。

2. **亚像素/重排引起的 1-2px 回退会被误判成用户操作**。补量行高、`remeasure_items` 之后
   滚动位置有 0.5px 级抖动，会被当成"上滚"。

Kimi 的做法（对照用）：`dist > 半屏` 才脱离，`dist <= 80px` 就吸附，中间带保持原状态，
再叠一个滚动方向判定。

### 改法

在 `Session` 层引入几何驱动的滞回判定，**不再让"输入方向"直接决定跟随**：

```rust
// session.rs 新增
/// 跟随判定的滞回带：距底这么多以内就吸附。
const FOLLOW_ATTACH: Pixels = px(80.);
/// 距底超过视口的这个比例才脱离。
const FOLLOW_DETACH_RATIO: f32 = 0.5;
/// 程序化滚动 / 跳转后这段时间内不重判（自己触发的位移不算用户操作）。
const FOLLOW_QUIET: Duration = Duration::from_millis(700);

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
enum FollowVerdict {
    /// 距离落在吸附带：恢复跟随
    Attach,
    /// 距离超过脱离带：放弃跟随
    Detach,
    /// 中间带：保持原状态（这是不抖的关键）
    Hold,
}

impl Session {
    /// 每帧在 `sync_list` 之后调用：按几何距离 + 方向决定跟随，而不是看输入。
    pub fn sync_follow(&mut self, now: Instant) {
        // 程序化滚动 / 跳转 / 滚轮还在推进中：自己动的不算
        if now < self.follow_quiet_until
            || self.wheel.is_some()
            || self.jump.is_some()
        {
            return;
        }
        let remaining = distance_to_end(&self.list);          // chat.rs:2555 已有
        let viewport = self.list.viewport_bounds().size.height;
        let detach = viewport * FOLLOW_DETACH_RATIO;
        let verdict = if remaining <= FOLLOW_ATTACH {
            FollowVerdict::Attach
        } else if remaining > detach {
            FollowVerdict::Detach
        } else {
            FollowVerdict::Hold
        };
        match verdict {
            FollowVerdict::Attach => {
                if !self.list.is_following_tail() {
                    self.list.set_follow_mode(FollowMode::Tail);
                    self.follow_quiet_until = now + FOLLOW_QUIET;
                }
            }
            FollowVerdict::Detach => {
                if self.list.is_following_tail() {
                    self.list.pause_following_tail();
                }
            }
            FollowVerdict::Hold => {}
        }
    }
}
```

配套改动：

- `chat.rs:2007` 和 `chat.rs:2039` 的 `pause_following_tail()` 调用**保留**，但改成"只在上滚位移
  累计超过 `FOLLOW_ATTACH` 后才压"——即把 `WheelInput` 的累计欠量也纳入判定，
  而不是第一格就压。最简单：删掉 `chat.rs:2039` 那段（几何判定接管），
  `chat.rs:2007` 保留作为"立刻响应"的快路径，但 `sync_follow` 会在 80px 内把它拉回来。
- 新字段 `follow_quiet_until: Instant`，在 `start_jump_to_bottom`、`follow_tail`、
  `reveal`、`set_follow_mode(Tail)` 里更新。
- `sync_follow` 的调用点：`content.rs:272` `sync_list` 之后、`step_wheel` 之前。

### 验收

- 单测（`session.rs` 测试模块，纯逻辑）：
  - 距底 79px 时 `pause_following_tail()` 后一帧恢复跟随
  - 距底 100px（< 半屏）保持原状态，不吸附也不脱离
  - 距底 > 半屏脱离
  - `follow_quiet_until` 内不改状态
- 手测：往上看 3 行，再往下滚，距离底 80px 时自动恢复跟随（不需要精确到底）。
- 手测：流式输出期间轻触触控板向上 2px，视口不回弹。

## 二、P1：三种"假滚动"甄别补全

### 现状

| 场景 | 现状 | 差距 |
|---|---|---|
| 指针在滚动条上 | `step_wheel` 检查 `is_scrollbar_dragging()`（`chat.rs:2034`） | 只影响滚轮推进，不影响跟随判定 |
| 指针在列表上按下 | 无 | 拖选文本时的小幅上滚会被算作脱离 |
| 内层滚动容器 | `scroll_tool_output` 能滚就吃，滚不动返回 false | **剩余 delta 被整格丢弃**，不还给外层 |

### 改法

**4a 指针按下状态**

```rust
// ChatApp 新增
/// 左键按住且起点在对话列表里：这期间的小幅上滚不算用户要脱离。
pointer_in_transcript: bool,
```

- `content.rs` 的 `wheel` canvas 里同时挂 `on_mouse_down(MouseButton::Left, ..)` / `on_mouse_up(..)`；
- `sync_follow` 里 `pointer_in_transcript` 为 true 时把 `Detach` 降级成 `Hold`。

**4b 内层滚到底后交还余量**

`chat.rs:921` `scroll_tool_output` 现在返回 `bool`。改成返回剩余：

```rust
/// 内层还能滚就吃掉这一格，返回 None；滚到底 / 到顶剩多少交还给外层。
pub(super) fn scroll_tool_output(
    &mut self, pos: Point<Pixels>, dy: Pixels, cx: &mut Context<Self>,
) -> Option<Pixels>;   // Some(remaining) = 没吃完，调用方接着走 wheel_by
```

调用点（`content.rs:355`）：

```rust
let leftover = this.scroll_tool_output(pos, dy, cx);
match leftover {
    Some(rest) => this.wheel_by(-rest, precise, cx),   // 余量交给外层，不丢
    None => { /* 内层吃干净 */ }
}
cx.stop_propagation();   // 两种情况都停，否则 bubble 再滚一次
```

这样内层滚到底之后，继续滚轮会平滑地带动外层，而不是"卡住 → 突然整格跳"。

### 验收

- 手测：指针放在展开的长工具输出上，一路往下滚到底，接着滚外层应连续跟手，不出现一格硬跳。
- 手测：在对话里按住左键往下拖选（选区会带动视口滚动），松开后跟随状态没变。

## 三、P2：键盘滚动

### 现状

`keys.rs:102` 的绑定表里没有任何滚动键。`PageUp` / `PageDown` / `Home` / `End` / 空格
只能靠焦点落到某个滚动容器上时由 gpui 内建处理；对话列表是虚拟列表，焦点通常在输入框，
所以这些键在对话区基本无效。

### 改法

复用 `wheel_by` 那一套，保证键盘和滚轮手感一致（这点很关键：两套手感会让人明显感到"不对"）：

```rust
// keys.rs
pub(super) const SCROLL_PAGE_UP_KEY: &str = "pageup";
pub(super) const SCROLL_PAGE_DOWN_KEY: &str = "pagedown";
pub(super) const SCROLL_TOP_KEY: &str = "home";
pub(super) const SCROLL_END_KEY: &str = "end";

actions!(chat, [ScrollPageUp, ScrollPageDown, ScrollToTop, ScrollToEnd]);
```

处理里：

- `PageUp` / `PageDown` / `Shift+空格` / `空格` → 折算成 `viewport_h * 0.85` 的像素，
  走 `wheel_by`（保持阻尼）；`PageUp` 方向额外 `pause_following_tail`
  （这里跟滚轮一样，交给 `sync_follow` 在 80px 内拉回）
- `Home` → `list.scroll_to(ListOffset { item_ix: 0, offset_in_item: 0 })` + `pause_following_tail`
- `End` → `follow_tail()`
- 焦点在输入框且输入框非空时**不拦**（空格是打字用），判据参考现有的
  `composer` 焦点状态

### 验收

- 手测：`PageDown` 连按 3 次的位移曲线和滚轮连滚 3 格一致（同为 `WheelInput` 阻尼）。
- 手测：输入框里打「a b」时空格正常输入。

## 四、P2：边缘渐隐连续化

### 现状

`session.rs:901` `ScrollEdge::of` 是四档离散：`Fits / Top / Middle / Bottom`，
`heights()` 直接返回 `(FADE_TOP, FADE_BOTTOM)` 的全有或全无。

后果：从顶部往下滚第 1px 时，顶上那条渐隐**突然**从 0 长到 `rems(1.)`。放大字号下这个跳变更明显。

### 改法

把 `ScrollEdge` 从上换成 `(f32, f32)` 的连续高度比例：

```rust
/// 上下两条渐隐的高度比例（0..=1）：贴顶时上面为 0，贴底时下面为 0，
/// 中间按离边的距离线性爬坡 —— 爬坡区取渐隐条自己的高度，滚满一条就饱和。
pub fn edge_fades(top: Pixels, remaining: Pixels, rem: Pixels) -> (f32, f32) {
    let fade_top = FADE_TOP.to_pixels(rem);
    let fade_bottom = FADE_BOTTOM.to_pixels(rem);
    let up = if fade_top > px(0.) { (top / fade_top).clamp(0., 1.) } else { 1. };
    let down = if fade_bottom > px(0.) { (remaining / fade_bottom).clamp(0., 1.) } else { 1. };
    (up, down)
}
```

`content.rs:329` 和 `content.rs:258` 的调用改成直接用比例乘高度。
`ScrollEdge` 保留（`sync_sidebar` 的指纹还用它），但只用于"要不要在指纹里区分"，不驱动高度。

### 验收

- 手测：从顶部滚 1px、5px、满一条高度，渐隐应该线性长出来。
- 手测：`Fits` 场景（内容不满一屏）两头都不画，与现在一致。

## 五、P2：跳转居中跟踪

### 现状

`session.rs:872` 的 reveal：

```rust
self.list.scroll_to(ListOffset { item_ix: ix, offset_in_item: px(0.) });
self.list.scroll_by(-px(24.));   // 让开顶上的渐隐
```

一次性定位。如果目标行里的图片 / 公式 / mermaid 之后才撑高，位置就偏了。

Kimi 的做法：跳转后 2 秒内每 120ms 复查一次，偏离中心 >48px 就再补。

### 改法

加一个短命跟踪器：

```rust
/// 跳转后的居中跟踪：目标行在 2s 内可能被异步内容撑高，偏了就再补一次。
pub struct RevealTrack {
    item_ix: usize,
    until: Instant,     // now + 2s
    next_check: Instant,// now + 480ms（首帧等图片/公式）
}
```

`render_content` 里每帧检查，偏离中心 >48px 就 `scroll_by(delta)`；命中 `until` 或行不在了就清掉。
只在 `reveal` / 搜索结果跳转时起。

### 验收

- 手测：搜索命中一条带长表格的回复，跳到它之后表格渲染完成，视野仍在同一段文字上。

## 六、P2：大回复按块拆行

### 现状（问题）

一条很长的已完成回复（上万字、几百行的表）是**一个虚拟行**：`render_item` 把整篇 Markdown
交给 `TextView`，列表排一行就要把整篇解析 + 排版一遍。256 行四列表实测滚动 p95 26.4–27.2ms，
卡在「一行」这个粒度上，虚拟列表帮不上忙。

### 改法

- `Session::rows: Vec<Row>`：`Row::Whole(记录下标)`（绝大多数）或 `Row::Part { src, part }`
  （很大的**已完成**回复拆成多行）。列表行数、`measured` 用行下标，`layout` / `transcript` 仍是记录下标，
  用 `Session::row_of` 换算。
- `split_markdown`：超过 4 KiB 才拆，每块约 2 KiB，在空行 / 块边界断；断在代码块里补围栏收尾、
  下一块带语言名重开；断在表格里重复表头两行。流式中最后一条不拆。
- 渲染：每块单独交给 `TextView`；回合末尾的复制 / 用时 / 改动卡片挂在最后一块；
  悬停、闪烁、`pin`、`reveal`、搜索结果都按 `row_of(记录)` 定位；元素 id 用行下标。
- 拆块只在记录形态变化时重算（条数 / 是否在跑 / 末尾回复长度），行划分变了重建列表并**按记录锚回原阅读位置**。

### 验收

- 单测：空行断块拼回原文、代码块围栏配平、表格块重复表头；大回复拆行后 `rows.item_count = 块数 + 1`，
  短回复和流式回复不拆。
- 性能：256 行四列表滚动 p95 目标 ≤12ms（基线 26.4–27.2ms），用 `CLAUDESKTOP_STRESS` 复测。
- 手测：长回复滚动不卡；搜索跳到长回复滚到第一块并闪烁；展开 / 收起卡片钉住行为不变。

## 七、P2：overscan 提升

### 现状

`session.rs:509` `ListState::new(1, ListAlignment::Top, px(600.))` —— 600px 固定，约半屏到一屏。

### 改法

600px → 按视口动态，保底 1200px：

```rust
// session.rs:509 附近改成建后按视口调整，或 new_list_state() 接受 viewport hint
const OVERDRAW_MIN: Pixels = px(1200.);

fn overdraw_for(viewport: Pixels) -> Pixels {
    (viewport * 3.).max(OVERDRAW_MIN)   // Kimi 用 ±3 屏
}
```

按 `list.rs:1482` 的实现，overdraw 是"额外布局多少高度"，调大会让单帧多布局几行——
按 HANDOFF 的基线（每帧 27 行、p95 2ms 级），3 屏大约 80 行仍在预算内，
但**必须重跑基线**再定数字，不能凭感觉。

### 验收

- 重跑 `.claudesktop/bench` 的对话滚动基线，p95 不超过现有值 +1ms。
- 手测：快速甩动滚轮，不应出现空白帧。

## 八、不做的事（附原因）

| 建议 | 不做的原因 |
|---|---|
| 引入 `overflow-anchor` 等价物 / 语义锚点 | GPUI 没有这个概念，`ScrollAnchor` 已经够用；新报告实测 Kimi 自己的锚点补偿也解决不了行内长高，换来的是一堆失效分支 |
| 布局签名收敛循环（每帧重贴底直到稳定） | 贴底由 `FollowMode::Tail` 的 item_count 锚点保证；补量行高造成的跳帧改用「拆块 + 估高」从根上消掉，不再靠每帧重贴掩盖 |
| 把 `follow_tail` 换自实现 | `list.rs` 的 item_count 锚点在流式追加时天然正确（末项一直长），自实现只会更差 |
| 复制 Kimi 的 `content-visibility: auto` | GPUI 没有离屏跳过渲染；项目已有的表格虚拟化 + 消息级虚拟化是同一目的的不同手段 |
| 给每个滚动区都上平滑 | 设置页 / 侧栏的 `WheelScroll`（`content.rs:126`）已经够用，且两者手感不同是对的（长文档 vs 短列表） |
